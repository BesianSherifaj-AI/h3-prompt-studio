# Local assistant evaluation — 9 September 2026

The expanded evaluation selected the installed **Qwen 3.8 27B Q4_K_S** as the final runtime candidate. It passed all 26 model cases in the repeated automatic suite, with two bounded corrections and a median of 9.26 seconds. Manual review still found a handoff/state contradiction and smaller continuity problems; this is not a universal quality score. The earlier Gemma and Qwen 9B comparisons below are retained as historical evidence, including their failures.

Initially, Gemma 4 12B QAT was substantially more reliable than the selected Qwen 3.5 9B variant. A separate load-configuration change reduced two measured Gemma turns from approximately 33–41 seconds to 9–10 seconds. These observations do not establish that any model never fails.

Gemma was selected in an isolated QA environment only. The evaluation did not change the user's live model selection or global LM Studio preferences. Each run created and released its own verified assistant instance. The final inventory check confirmed that no evaluation instance remained loaded. The harness did not generate assets, submit ComfyUI render jobs, or download models.

The machine was an NVIDIA GeForce RTX 4090 with 24,564 MiB reported VRAM. Both models used an 8,192-token loaded context, temperature 0.55, and the existing production actor/writer/director prompts. Output limits were 450 actor tokens, 1,800 narrative tokens, and 1,400 director tokens. The compatible endpoint requested `reasoning_effort: none`; the inspected stage usage reported zero reasoning tokens. The model keys were exact installed keys:

- `qwen3.5-9b-uncensored-hauhaucs-aggressive@q4_k_m`, approximately 6.55 GB of model files.
- `google/gemma-4-12b-qat`, Q4_0, approximately 7.15 GB of model files.

The baseline ran twelve synthetic cases once per model: combat attempt, pickup, drop, give, open door, locked-door button guard, freeform locked-door attempt, explicitly addressed NPC among bystanders, exact Albanian quotation, opening from a text premise without accepted location state, long event history, and Studio author mode. The locked-door button is a deterministic guard case: it correctly rejected the unavailable action before inference for both models. It is excluded from the eleven model-case denominator.

- Qwen completed **2 of 11** model cases with valid pipeline output; nine were blocked. Median case time was **13.89 seconds**. Because most cases failed before the director, this median is not a comparable measure of full-turn generation speed.
- Gemma completed **10 of 11** model cases with valid pipeline output; one was blocked. Median case time was **33.49 seconds**. All 31 attempted stages passed their response schemas.
- Qwen's 22 attempted stages included 21 schema-valid responses. Its frequent failures happened after JSON validation: four empty beat identifiers, two duplicate existing characters, one missing selected interaction, and one conflicting discovery. One actor response exceeded its speech budget after the bounded JSON correction.
- Gemma's blocked Studio case had a usable authored action but an empty optional next-choice message. The narrative validator rejected the whole result.

“Valid pipeline output” means JSON/schema checks and the production planning invariants completed. It is not a rating of writing, acting, or complete semantic correctness. Manual inspection found these additional issues:

- Both models turned the long-history request to **examine** a key into **picking it up**, including a holder change, despite the request stating that the key was on the workbench. These two baseline cases passed the then-current automatic checks but failed this semantic requirement. The harness now includes an explicit possession-preservation invariant for this scenario; the original baseline reports have been preserved without rewriting their scores.
- Qwen retained the exact player's Albanian quotation, but its NPC produced Albanian-like text labeled as English. The label and the words did not match. Exact player-word preservation alone did not catch this.
- Both models introduced scene drift around opening the door: describing the workshop as being newly revealed even though the player was already inside, or putting the key on the floor in an optional suggestion despite its workbench placement.
- Gemma generally produced coherent resistance to combat and correct pickup/drop/give effects, and chose the specifically addressed Mira ahead of unrelated bystanders. Its actors mostly answered nonverbally. That is allowed by the current actor contract, but sustained conversational engagement requires a separate dialogue-focused evaluation.

The latency investigation found a concrete configuration problem. While Gemma's model layers were fully offloaded (`gpu.ratio: 1.0`), its loaded SDK profile reported `offloadKVCacheToGpu: false`; the native REST inventory independently reported `offload_kv_cache_to_gpu: false`. Roughly 8.1 GB of the available GPU memory was in use. The application had explicitly selected context length and Flash Attention while inheriting the model's CPU KV-cache setting. LM Studio documents that a false KV-offload setting stores the cache in CPU memory/RAM, and supports specifying it per load. [LM Studio load API](https://lmstudio.ai/docs/developer/rest/load)

Owned exclusive assistant loads now explicitly request GPU KV-cache placement and verify the returned configuration through the SDK or authenticated REST response. The dedicated resident CPU profile continues to request and verify CPU KV storage. Ordinary standalone loads preserve their existing default behavior unless the caller explicitly supplies a placement option.

Two Gemma cases were then rerun with the verified GPU cache enabled:

- **Combat attempt:** 41.17 seconds baseline; **9.17 seconds** afterward.
- **Addressed NPC:** 33.49 seconds baseline; **9.84 seconds** afterward.
- The matched baseline stages generated 1,171 completion tokens in 74.65 measured stage seconds: **15.69 effective output tokens/second**. The follow-up generated 1,293 completion tokens in 18.99 stage seconds: **68.09 effective output tokens/second**.
- Preparation took 8.64 seconds in the baseline model run and 6.85 seconds in the follow-up. Adding preparation to the two matched case durations gives **83.29 seconds baseline versus 25.85 seconds follow-up**. The follow-up's measured model interval was **26.69 seconds**, including preparation and inter-case coordination, before final unload. The baseline matched cases occurred at separate points in the larger suite, so their 83.29-second figure is a sum of measured components, not a contiguous wall-clock interval.
- Both follow-up cases passed all six stage schemas and the planning checks. Manual review found a coherent blocked punch and a relevant gesture toward the requested mechanical issue.

Effective output throughput here is the sum of completed response tokens divided by the sum of measured request-stage durations. It includes prompt processing, transport, and local validation. It is **not isolated decoder throughput**, does not measure image encoding or rendering, and does not count unreported partial tokens on failed requests.

This is **not a controlled causal benchmark of KV placement alone**. Each case was sampled once at nonzero temperature, output lengths differed, prompt/cache warmness was not reset or randomized, and beat/schema hardening also landed between the runs. The objective observations are the false-to-true loaded configuration change, the recorded outputs, and the measured timing difference. A repeated, randomized A/B experiment with frozen code, identical prompts and controlled cache state would be needed to attribute a precise speedup to KV placement alone.

At that stage, Gemma 4 12B QAT was selected for further QA based on the initial comparison and faster follow-up. Google's official model card confirms a 12B model with multimodal input, native system-role support and configurable thinking. Those capabilities are not evidence that it obeys every game rule. This initial comparison concerns one particular modified Qwen 9B quantization; the later 27B results below demonstrate why it must not be generalized to all Qwen models. [Google Gemma 4 model card](https://ai.google.dev/gemma/docs/core/model_card_4)

The baseline predates the subsequent application changes that assign known pickup/drop/give/open/close/examine/look/move mechanics to deterministic game code and ask the model only to direct their presentation. Dialogue, combat, unknown actions and initial world creation remain creative planning tasks. Beat identifiers, duplicate established-character handling and optional Studio choices have also been hardened. The two GPU-cache follow-ups exercised the creative path only. The baseline scores must not be presented as a measurement of the new mechanical route or as a full post-fix regression run.

The reusable harness is [evaluate_game_assistant.py](../scripts/evaluate_game_assistant.py). It writes complete stage requests, raw response diagnostics, schema outcomes, pipeline errors and timing to a fresh output directory. It refuses to adopt a model already loaded by another session and retains its own instance for inspection after a timeout, disconnect or interrupt rather than claiming that a socket failure proves inference stopped. Unit coverage includes those boundaries; it does not substitute for the live evaluation.

Raw local evidence is intentionally kept outside the release repository, under the neutral run directories `model-eval` and `model-eval-gpu-kv` in the local research workspace. The relevant files are `model-eval/report.json`, `model-eval/gemma-baseline-load-config.json`, individual `model-*.json` case records, `model-eval-gpu-kv/report.json`, `model-eval-gpu-kv/comparison.json`, and `model-eval/manual-review.json`. These reports contain synthetic evaluation prompts and local model inventory. No machine-specific absolute paths or private live-project data are embedded in this document.

New harness runs use **evaluation version 2**. After narrative and direction validation, they prepare the actual directed project and run `compile_project`, saving the compiled prompt, compiler issues, preparation/compilation time and project. A case cannot pass unless `compiled.valid` is true. This catches responses that satisfy the narrative schema but cannot form an H3 prompt, including dialogue with an empty language label. Version 2 also corrects the fixture's old `t2v` mode spelling to H3's supported `t2va`. The preserved version 1 results above measure planning validity only; they do **not** demonstrate H3 prompt or render readiness. Their original scores have not been retroactively changed.

## Expanded repeated evaluation and selection

Gemma's full version 2 run (`model-eval-final`) passed **22/26** model cases, with all 26 compiling and both no-inference guards working. Median time was **8.89 seconds**. Both repeats of the inspection and direct factual question failed behavior checks: inspection became pickup, while the knowledgeable cooperative NPC expressed an intention to answer without actually speaking. A targeted six-case run with one semantic repair enabled passed **1/6**, exposing both model errors and overly strict handling of unused optional exception metadata. These records remain unchanged; targeted production guards were corrected afterward.

The installed vision-capable `qwen3.8-27b@q4_k_s` is reported by the local server as an Unsloth Q4_K_S quantization, 27B parameters and **17,048,970,576 bytes** of model files. It uses the same 8,192-token context and verified exclusive GPU cache placement. Its first two-case diagnostic passed both difficult cases without correction, with median **9.58 seconds**. No new model was downloaded.

The final repeated run (`model-eval-qwen27-final`) then covered all fourteen cases twice, explicitly using the harness's optional `--semantic-repair` policy:

- **26/26 model cases** passed automatic invariants and final H3 compilation; both deterministic locked-door guards rejected before inference.
- All **78 stage calls** passed their schemas. There were **two semantic corrections**: removing movement to an unknown room during door opening, and including a speaking character in the directed scene. Earlier successful stages were reused; transport uncertainty was never retried automatically.
- Median model-case time was **9.26 seconds**. Initial preparation took **11.12 seconds**; the complete run including preparation took **269.06 seconds**. Effective output throughput was **54.74 tokens/second**, including prompt processing and validation.
- The preparation snapshot reported **21,256 MiB GPU memory used** and **2,883 MiB free** on this 4090. This is a machine-specific observation, not a memory guarantee for larger images or contexts.

Manual review confirmed actual spoken factual answers, untouched inspected keys, grounded combat consequences, preserved player quotations and Studio direction in the checked records. It also found a material contradiction in the second creative give case: the narrative put the key on the bench while the effect still named Mira as holder. Other outputs inconsistently pocketed versus held a key, embellished a room revealed behind a door, or introduced spatial details only in prose. A final prompt clarification now explicitly ties effects to the terminal outcome after all NPC actions. The original full-run score and counterexample are retained; automatic success is not equated with perfect scenes.

The automatic give fixture expects its selected handoff effect. A legitimate NPC placing an offered item down may require a different final holder, so that check is narrower than arbitrary authored gameplay. Read the full trajectory and manual review. The actual application's fast-mechanics handoff was also separately rendered and verified visually and in saved state; those results are documented in [VALIDATION_2026-09-09.md](VALIDATION_2026-09-09.md).

After the terminal-holder clarification, a separate four-case run (`model-eval-terminal-holders`, give/drop twice each) passed **4/4**, with **zero semantic repairs** and median **9.46 seconds**. Manual review found both handoffs ending with Mira holding the key and both drops ending unheld in the workshop, consistently with their effects. One drop's wooden-surface/floor wording remained imprecise. This is a focused follow-up, not a rerating of the original 26 cases.

These runs are not randomized model benchmarks: code, correction policy, prompt warmth and outputs changed across stages of development. They support this local model/configuration choice and reveal concrete failures, without establishing a general ranking of model families or zero-failure behavior.
